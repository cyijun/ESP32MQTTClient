# Review criteria

Review by whether the reader can complete an outcome, not whether every template heading exists.

## Newcomer test

A professional engineer with no repository context should answer the following after three to five linked pages: what the product or feature does, how to run or use it safely, where its state lives, which component owns it, how it fails, and where to change it. If the reader must inspect source merely to discover the public flow, restore the missing explanation. If the reader must absorb unrelated internals, move those details deeper.


## Evidence and scope

Use project metadata for names/entry points, public interfaces for caller obligations, runtime code for implementation, tests for exercised cases, generated catalogs for inventories, and active decisions for rationale. A test file’s existence is not a passing run. Static inspection supports a qualified implementation description; a successful-operation claim requires execution evidence. Unavailable credentials or unsafe side effects are explicit verification limits, not reasons to fabricate results.

A package README explains when to choose it, prerequisites, its actual use path, observable success, relevant failures and limitations, and where implementation detail lives. Identify whether the subject is a library, service, application, or plugin before writing install guidance. No mandatory runtime vocabulary or project-specific headings apply.

## Review the initialization itself

Confirm applicable copied skills were read in this turn before drafting. Inspect materialized documents against their evidence. Identify at least one specific application of complete-proposition preservation, fact ownership, and session-independent prose; do not accept a boilerplate “review passed.” Check existing ADRs and user instructions survived. Run the configured checker, then report its limits separately from semantic review.
